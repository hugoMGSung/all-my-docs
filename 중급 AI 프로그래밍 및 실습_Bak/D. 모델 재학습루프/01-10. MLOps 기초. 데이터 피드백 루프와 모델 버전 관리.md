
## 들어가며

앞 장에서는 해양 관측 데이터를 Chart.js로 시각화했습니다. 이번 장에서는 AI 모델을 한 번 학습하고 끝내지 않고, 서비스에서 얻은 데이터를 바탕으로 개선하는 **MLOps의 기초**를 살펴봅니다.

MLOps는 머신러닝 모델을 개발·배포·운영하는 과정을 반복 가능하고 추적 가능하게 관리하는 방법입니다. 오늘은 서비스의 예측 결과와 사용자 검토를 다시 학습 데이터로 연결하는 데이터 피드백 루프를 설계하고, Git과 Docker를 사용해 코드와 실행 환경의 버전을 관리합니다.

## 1. MLOps란?

머신러닝 프로젝트는 모델 파일 하나만으로 운영되지 않습니다. 데이터, 전처리 코드, 학습 설정, 모델, API, 배포 환경이 함께 맞아야 합니다.

```text
데이터 수집
   ↓
학습 데이터 검토·정제
   ↓
모델 학습·평가
   ↓
모델 등록·버전 지정
   ↓
서비스 배포
   ↓
운영 모니터링·사용자 검토
   └──────── 피드백을 다음 학습으로 전달
```

MLOps의 목표는 이 과정을 관리해 다음 질문에 답할 수 있게 하는 것입니다.

- 현재 서비스에서 어떤 모델이 사용되고 있나요?
- 그 모델은 어떤 데이터와 코드로 만들어졌나요?
- 이전 모델보다 성능이 좋아졌나요?
- 문제가 생기면 이전 모델이나 배포 상태로 되돌릴 수 있나요?
- 새 모델을 서비스에 반영한 뒤 결과가 달라졌나요?

## 2. 데이터 피드백 루프 이해하기

운영 중인 모델이 반환한 결과를 사용자가 확인하거나 정답 정보를 추가하면, 그 자료를 다음 학습에 활용할 수 있습니다.

```text
이미지 입력
   ↓
모델 예측: 참돔, confidence 0.62
   ↓
전문가 검토: 실제 정답은 방어
   ↓
검토된 예시를 학습 자료에 추가
   ↓
새 모델 학습·평가
   ↓
검증 통과 모델만 배포
```

모델의 예측을 그대로 정답으로 저장하면 잘못된 결과가 학습 데이터에 섞일 수 있습니다. 정답은 전문가 검토, 신뢰할 수 있는 센서·라벨 정보, 별도의 확인 절차를 통해 확정해야 합니다.

## 3. 피드백 데이터를 기록할 구조 정하기

예측 결과와 검토 결과는 목적이 다르므로 필드를 분리해 기록합니다.

```json
{
  "observationId": "obs-001",
  "imageUrl": "/uploads/obs-001.jpg",
  "predictedLabel": "참돔",
  "confidence": 0.62,
  "modelVersion": "fish-classifier-v1.2.0",
  "review": {
    "status": "confirmed",
    "correctedLabel": "방어",
    "reviewedBy": "reviewer-01",
    "reviewedAt": "2026-12-01T03:20:00.000Z"
  },
  "datasetStatus": "eligible"
}
```

`predictedLabel`은 모델의 예측이고 `correctedLabel`은 확인을 거쳐 정해진 정답입니다. `modelVersion`을 함께 저장하면 어떤 모델이 해당 결과를 만들었는지 추적할 수 있습니다.

개인정보나 불필요한 식별 정보는 수집하지 않습니다. 이미지를 학습에 재사용할 수 있는 권한과 보관 정책도 데이터 파이프라인을 만들 때 확인해야 합니다.

## 4. 피드백 데이터 상태 관리하기

검토 자료는 한 번에 모두 학습에 넣기보다 상태에 따라 관리합니다.

| 상태 | 의미 | 다음 처리 |
|---|---|---|
| `pending` | 검토 대기 중 | 검토자에게 확인 요청 |
| `confirmed` | 정답 확인 완료 | 재학습 후보로 평가 |
| `rejected` | 품질 문제나 라벨 오류로 제외 | 제외 사유 기록 |
| `eligible` | 학습 데이터 사용 조건 통과 | 버전이 지정된 데이터셋에 포함 |
| `used` | 특정 학습 실행에 사용됨 | 학습 기록에 데이터셋 버전 연결 |

신뢰도 낮은 예측은 검토 우선순위를 정하는 데 활용할 수 있습니다. 다만 낮은 신뢰도 자체가 오분류를 의미하지는 않습니다. 검토 기준을 정하고 확인 결과를 별도 기록합니다.

## 5. 모델 버전이 필요한 이유

모델 버전은 서비스에서 사용한 모델 파일과 학습 결과를 구분하는 식별자입니다. 모델 파일을 매번 `model.pt`로 덮어쓰면 이전 결과와 비교하거나 문제를 되돌리기 어렵습니다.

버전을 붙이는 한 가지 예는 다음과 같습니다.

```text
fish-classifier-v1.0.0
fish-classifier-v1.1.0
fish-classifier-v2.0.0
```

또는 날짜와 학습 실행 ID를 함께 사용할 수 있습니다.

```text
fish-classifier-2026-12-01-run-004
```

버전은 모델 파일명만으로 끝나지 않습니다. 최소한 다음 메타데이터를 함께 기록합니다.

```json
{
  "modelName": "fish-classifier",
  "modelVersion": "1.2.0",
  "createdAt": "2026-12-01T04:00:00.000Z",
  "datasetVersion": "marine-dataset-v3",
  "sourceCodeCommit": "a1b2c3d",
  "framework": "PyTorch",
  "inputSize": [224, 224],
  "classes": ["참돔", "광어", "방어"],
  "evaluation": {
    "accuracy": 0.91,
    "macroF1": 0.88
  }
}
```

실제 운영에서는 정확도 외에도 클래스별 정밀도·재현율, 혼동행렬, 데이터 분포 등을 검토할 수 있습니다. 모델을 배포할지는 프로젝트에서 정한 평가 기준과 검증 절차를 따릅니다.

## 6. Git으로 코드와 설정 이력 관리하기

Git은 소스 코드와 설정 변경 내역을 추적합니다. 모델 학습이나 추론 전처리 코드가 달라졌다면 해당 코드가 어떤 커밋인지 기록해야 합니다.

프로젝트가 아직 Git 저장소가 아니라면 초기화합니다.

```bash
git init
git status
```

`.gitignore`에 생성 파일과 비밀 정보를 추가합니다.

```text
node_modules/
.venv/
__pycache__/
.env
*.log
```

코드를 커밋합니다.

```bash
git add server.js ai_server package.json package-lock.json .gitignore
git commit -m "Add inference service baseline"
```

모델 버전을 배포할 기준점으로 표시할 수 있습니다.

```bash
git tag model-v1.2.0
git log --oneline --decorate -5
```

Git은 큰 모델 바이너리나 대규모 데이터셋 저장소로 쓰기에 적합하지 않을 수 있습니다. 모델 파일을 저장할 별도 저장소나 아티팩트 저장 위치를 정하고, Git에는 모델 식별자·체크섬·메타데이터·저장 위치를 기록할 수 있습니다. 중요한 것은 코드 커밋과 모델 파일 버전이 서로 연결되도록 하는 것입니다.

## 7. 데이터셋 버전과 누수 방지

데이터셋의 원본 파일을 덮어쓰지 않고, 어떤 자료가 학습에 포함됐는지 기록합니다.

```text
data/
├─ raw/                 # 원본 데이터, 읽기 전용으로 보관
├─ reviewed/            # 정답 검토가 끝난 자료
└─ manifests/
   ├─ marine-v1.csv
   └─ marine-v2.csv
```

Manifest는 데이터 파일의 목록이나 버전, 체크섬, 라벨 상태를 기록하는 파일입니다. 원본을 보존하고 전처리 결과를 별도 생성하면 같은 입력으로 변환 과정을 다시 실행하기 쉽습니다.

학습·검증·테스트 데이터가 중복되거나, 같은 개체의 비슷한 이미지가 서로 다른 분할에 들어가면 모델 성능을 실제보다 높게 평가할 수 있습니다. 데이터를 분할할 때는 해당 데이터의 특성에 맞는 기준을 세우고 중복이나 누수를 확인합니다.

## 8. Docker로 실행 환경 고정하기

Docker는 애플리케이션과 실행 환경을 이미지로 묶어 같은 구성으로 실행할 수 있게 합니다. 이 차시에서는 전체 서비스를 컨테이너로 묶기보다, FastAPI 추론 서버의 기본 실행 환경을 고정하는 예를 봅니다. 전체 Node.js·FastAPI·MongoDB 통합은 13일차에 다룹니다.

`ai_server/Dockerfile` 예시:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

COPY . ./ai_server

EXPOSE 8000

CMD ["uvicorn", "ai_server.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`requirements.txt`에는 서버와 모델 실행에 필요한 라이브러리를 기록합니다. 실제 배포에서는 Python과 주요 패키지의 버전을 프로젝트에서 검증한 값으로 고정합니다.

이미지를 빌드하고 실행합니다.

```bash
docker build -t fish-inference:v1.2.0 .
docker run --rm -p 8000:8000 fish-inference:v1.2.0
```

CPU용 PyTorch와 GPU용 PyTorch는 환경 구성이 다를 수 있습니다. GPU가 필요한 모델이라면 컨테이너 베이스 이미지, CUDA 호환성, 실행 장비를 함께 확인해야 합니다. 오늘은 같은 실행 환경을 다시 만들고 모델 버전 태그를 지정하는 원리를 익힙니다.

## 9. 학습·배포 기록 남기기

새 모델을 만들 때마다 다음 항목을 기록하면 결과를 비교하고 재현하는 데 도움이 됩니다.

- 모델 버전과 모델 파일 위치 또는 체크섬
- 학습 데이터셋 버전과 사용한 데이터 수
- 학습 코드 Git 커밋
- 전처리 설정과 클래스 목록
- 평가 결과와 승인 여부
- Docker 이미지 태그와 배포 시각

예를 들어 `model-v1.2.0`이 어떤 데이터와 코드로 만들어졌는지 찾을 수 있어야 합니다. 기록이 연결되지 않으면 문제가 생겼을 때 모델 파일, 코드, 데이터를 맞춰 보기 어렵습니다.

## 10. 피드백 루프 운영 시 주의할 점

자동으로 새 데이터를 계속 추가하는 것만으로 모델이 개선되지는 않습니다. 다음 위험을 관리해야 합니다.

- 정답이 확인되지 않은 예측을 학습 정답으로 오인하는 문제
- 특정 양식장이나 촬영 조건의 데이터만 많이 모이는 편향
- 중복 이미지와 잘못된 라벨이 누적되는 문제
- 새 모델의 전체 성능은 좋아져도 특정 어종의 성능이 나빠지는 문제
- 모델 버전과 전처리 버전이 맞지 않는 문제
- 이전 모델로 되돌릴 파일과 실행 방법이 없는 문제

새 모델은 현재 운영 모델과 비교하고, 정해 둔 기준을 통과했을 때 배포합니다. 배포 후 결과를 관찰하고 문제가 확인되면 이전 버전으로 되돌릴 수 있도록 합니다.

## 실습: 데이터 피드백과 모델 버전 기록 만들기

다음 항목을 프로젝트에 추가합니다.

- 예측 결과에 `modelVersion`을 기록합니다.
- 검토 상태와 수정된 정답 라벨을 저장할 구조를 설계합니다.
- `pending`, `confirmed`, `rejected`, `eligible` 처리 흐름을 작성합니다.
- 모델 메타데이터 JSON에 데이터셋 버전과 Git 커밋을 기록합니다.
- Git 저장소에서 `.env`, 가상환경, 로그를 제외합니다.
- FastAPI 컨테이너 이미지를 모델 버전 태그로 빌드하고 실행합니다.

## 오늘의 미션

- MLOps 흐름에서 데이터 피드백이 필요한 이유를 설명합니다.
- 예측 라벨과 검토된 정답을 구분해 저장합니다.
- 모델 버전과 데이터셋 버전, 코드 커밋을 연결합니다.
- Git으로 코드 변경 이력과 모델 릴리스 기준점을 관리합니다.
- Docker 이미지 태그를 이용해 실행 환경을 구분합니다.
- 새 모델을 배포하기 전에 검증해야 할 기준을 정합니다.

## 핵심 정리

- MLOps는 데이터부터 운영 모델까지의 머신러닝 과정을 추적하고 반복 가능하게 관리합니다.
- 데이터 피드백 루프는 운영 결과와 검토된 정답을 다음 학습으로 연결합니다.
- 모델의 예측과 확인된 정답은 별도의 필드로 보관해야 합니다.
- 모델·데이터셋·코드·실행 환경의 버전을 서로 연결해야 결과를 재현할 수 있습니다.
- Git은 코드와 설정 변경을 추적하고, Docker는 실행 환경을 이미지로 고정하는 데 도움을 줍니다.
- 새 모델은 검증 후 배포하고, 문제 발생 시 이전 버전으로 되돌릴 수 있게 준비합니다.
- 다음 수업에서는 웹 서비스 보안의 JWT와 클라우드 배포 전략을 살펴봅니다.
