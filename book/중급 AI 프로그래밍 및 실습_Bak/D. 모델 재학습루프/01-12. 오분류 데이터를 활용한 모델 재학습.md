
## 들어가며

앞 장에서는 JWT로 API를 보호하고 클라우드 배포를 준비했습니다. 이번 장에서는 서비스에서 발생한 AI 예측 오류를 기록하고, 확인된 오분류 데이터를 새로운 학습 자료로 활용하는 **모델 재학습 프로세스**를 살펴봅니다.

운영 중 수집한 예측 결과를 바로 학습에 넣는 것이 아니라, 정답을 검토하고 데이터 품질을 확인한 뒤 기존 모델과 비교 평가해야 합니다. 오늘은 오분류 보고부터 재학습·검증·버전 기록까지 한 번의 반복 가능한 흐름으로 구성합니다.

## 1. 오분류 데이터가 중요한 이유

학습 데이터가 대표하지 못했던 환경이 실제 서비스에서 나타날 수 있습니다. 예를 들어 수중 조명, 탁도, 카메라 각도, 어종의 크기가 학습 때와 다르면 모델이 잘못 분류할 수 있습니다.

```text
실제 서비스 입력
   ↓
모델 예측 결과 저장
   ↓
사용자 또는 전문가 검토
   ↓
정답 라벨과 오류 유형 확정
   ↓
품질 검사·중복 제거
   ↓
학습 후보 데이터셋에 추가
   ↓
새 모델 학습·평가
   ↓
승인된 모델만 배포
```

이 흐름은 서비스 운영에서 얻은 경험을 모델 개선에 반영하는 데이터 피드백 루프입니다. 예측값 자체를 정답으로 간주하지 않고, 검토된 정답 라벨을 별도로 저장하는 것이 핵심입니다.

## 2. 서비스에서 오분류를 보고하는 데이터

검토 데이터는 원본 관측 정보와 예측 정보, 검토 정보를 연결해야 합니다.

```json
{
  "observationId": "obs-001",
  "imageUrl": "/uploads/obs-001.jpg",
  "predictedLabel": "참돔",
  "confidence": 0.62,
  "modelVersion": "fish-classifier-v1.2.0",
  "review": {
    "status": "confirmed",
    "correctedLabel": "방어",
    "reviewedAt": "2026-12-01T03:20:00.000Z",
    "reviewedBy": "reviewer-01",
    "reason": "유사한 체형의 어종으로 오분류"
  },
  "datasetStatus": "eligible"
}
```

`predictedLabel`은 모델의 답이고 `correctedLabel`은 검토로 확인된 정답입니다. `modelVersion`을 함께 기록하면 어느 모델이 만든 예측이 틀렸는지 분석할 수 있습니다.

## 3. 검토 상태를 관리하는 API

다음은 관리자나 검토자가 검토 완료 라벨을 저장하는 예시입니다. 이 경로에는 인증과 역할 권한 확인이 적용되어야 합니다.

```javascript
app.patch(
  "/api/admin/reviews/:observationId",
  requireAuth,
  requireRole("reviewer", "admin"),
  async (request, response, next) => {
    try {
      const { observationId } = request.params;
      const { correctedLabel, reason } = request.body;
      const allowedLabels = ["참돔", "광어", "방어"];

      if (!allowedLabels.includes(correctedLabel)) {
        return response.status(400).json({
          message: "등록되지 않은 어종 라벨입니다."
        });
      }

      const db = getDatabase();
      const result = await db.collection("observations").updateOne(
        { _id: new ObjectId(observationId) },
        {
          $set: {
            review: {
              status: "confirmed",
              correctedLabel,
              reason: reason ?? "",
              reviewedBy: request.user.id,
              reviewedAt: new Date()
            },
            datasetStatus: "eligible"
          }
        }
      );

      if (result.matchedCount === 0) {
        return response.status(404).json({ message: "관측 자료가 없습니다." });
      }

      response.json({ message: "검토 결과를 저장했습니다." });
    } catch (error) {
      next(error);
    }
  }
);
```

예제는 관측 데이터를 수정해 검토 결과를 저장합니다. 실제 시스템에서는 검토 권한, 라벨 목록, 감사 기록, 중복 검토 정책, 이미지 접근 권한 등을 추가로 설계해야 합니다. 데이터베이스의 식별자가 MongoDB ObjectId 형식인지도 먼저 확인해야 합니다.

## 4. 학습에 사용할 데이터 고르기

검토가 완료된 자료 중에서도 모든 자료를 자동으로 학습에 넣지는 않습니다. 다음 기준을 확인합니다.

- 이미지가 정상적으로 열리고 필요한 해상도를 갖는가?
- 정답 라벨이 승인된 어종 목록에 포함되는가?
- 이미지와 라벨이 정확히 연결되어 있는가?
- 같은 이미지나 거의 같은 프레임이 중복되지 않는가?
- 학습에 사용할 권한과 보관 정책을 충족하는가?
- 기존 학습 데이터와 검증 데이터에 중복이 생기지 않는가?

조건을 통과한 데이터만 `eligible` 상태로 지정합니다. 제외한 데이터는 이유를 기록해 나중에 품질 문제를 분석할 수 있도록 합니다.

## 5. 데이터셋 버전 만들기

재학습 결과를 비교하려면 어떤 자료가 사용됐는지 알아야 합니다. 데이터셋의 원본은 보존하고, 학습에 포함한 파일 ID와 라벨을 Manifest로 기록할 수 있습니다.

```csv
observationId,imagePath,label,source,reviewedAt
obs-001,images/obs-001.jpg,방어,service-review,2026-12-01T03:20:00Z
obs-014,images/obs-014.jpg,광어,service-review,2026-12-02T05:10:00Z
```

데이터셋 버전 예시:

```text
dataset-marine-v1    초기 검토 완료 자료
dataset-marine-v2    운영 검토 자료 추가
```

Manifest에 데이터셋 버전, 자료 수, 생성 시각, 라벨 정의와 파일 체크섬 등을 기록하면 학습 입력을 다시 구성하는 데 도움이 됩니다. Git은 코드와 Manifest를 추적할 수 있지만, 대형 이미지 파일은 별도 아티팩트 저장소를 사용할 수 있습니다.

## 6. 학습·검증·테스트 데이터 나누기

재학습 평가 자료가 학습 자료와 겹치면 성능을 실제보다 높게 추정할 수 있습니다. 새로 수집한 자료를 무작위로 섞기 전에 동일 이미지, 연속 프레임, 동일 개체 사진이 여러 분할에 들어가지 않도록 확인합니다.

```text
학습 데이터 (train)
모델 가중치를 조정하는 데 사용

검증 데이터 (validation)
학습 중 설정과 후보 모델을 비교하는 데 사용

테스트 데이터 (test)
최종 성능을 독립적으로 확인하는 데 사용
```

데이터 수가 적다면 검증 결과의 불확실성이 큽니다. 학습 자료를 나눌 기준과 각 분할 자료 수를 기록합니다. 같은 개체의 연속 이미지가 있다면 촬영 세션이나 개체 단위로 분리해 데이터 누수를 줄이는 방법을 고려합니다.

## 7. 재학습 실행하기

재학습은 기존 모델을 새 자료에 맞게 갱신하거나, 기존 학습 자료와 검토 자료를 함께 사용해 다시 학습하는 과정입니다. 학습 방식은 데이터 양과 학습 파이프라인에 따라 달라집니다.

재학습 전에는 입력 전처리, 클래스 목록, 모델 구조가 현재 서비스와 맞는지 확인합니다. 학습 설정은 파일로 관리합니다.

```json
{
  "datasetVersion": "dataset-marine-v2",
  "baseModelVersion": "fish-classifier-v1.2.0",
  "imageSize": [224, 224],
  "epochs": 10,
  "batchSize": 32,
  "seed": 42,
  "classes": ["참돔", "광어", "방어"]
}
```

학습 스크립트는 입력 데이터 경로와 출력 경로를 인자로 받도록 만들 수 있습니다.

```bash
python train.py \
  --manifest data/manifests/dataset-marine-v2.csv \
  --base-model artifacts/fish-classifier-v1.2.0.ts \
  --output artifacts/fish-classifier-v1.3.0.ts \
  --config configs/retrain-v2.json
```

명령줄의 옵션 이름은 프로젝트 학습 스크립트에 맞춰 정의합니다. 위 코드는 재학습 실행 흐름을 보여주는 예시입니다. 모델 파일을 저장할 때는 기존 운영 모델을 덮어쓰지 않고 새 버전 이름으로 출력합니다.

## 8. 후보 모델 평가하기

새 모델이 만들어졌다고 바로 배포하지 않습니다. 같은 평가 자료에서 현재 운영 모델과 후보 모델을 비교합니다.

| 평가 항목 | 확인 목적 |
|---|---|
| 전체 정확도 | 전체 예측 중 맞힌 비율 |
| 클래스별 정밀도·재현율 | 특정 어종을 과하게 예측하거나 놓치는지 확인 |
| 혼동 행렬 | 어떤 어종끼리 혼동하는지 확인 |
| 신뢰도 분포 | 낮은 신뢰도 결과가 어느 조건에 모이는지 확인 |
| 추론 시간 | 기존 서비스 지연을 크게 늘리지 않는지 확인 |

예를 들어 전체 정확도가 올라도 방어의 재현율이 크게 떨어질 수 있습니다. 평가 기준은 서비스에서 중요한 어종과 오류 비용을 고려해 정합니다.

## 9. 승인 후 모델 등록하기

검증을 통과한 후보 모델은 메타데이터와 함께 등록합니다.

```json
{
  "modelName": "fish-classifier",
  "modelVersion": "1.3.0",
  "status": "candidate",
  "datasetVersion": "dataset-marine-v2",
  "sourceCodeCommit": "d4e5f6a",
  "baseModelVersion": "1.2.0",
  "createdAt": "2026-12-03T06:00:00.000Z",
  "evaluation": {
    "accuracy": 0.92,
    "macroF1": 0.89,
    "approved": true
  }
}
```

`candidate`, `staging`, `production`, `archived`와 같은 상태를 두어 모델 생명주기를 관리할 수 있습니다. 승인자는 평가 결과와 사용 조건을 확인한 뒤 운영 버전으로 지정합니다.

## 10. Git과 Docker로 재학습 재현하기

Git은 학습 코드, 설정, Manifest의 변경을 추적합니다. 학습 실행에 사용한 커밋 ID를 기록하면 코드를 다시 확인할 수 있습니다.

```bash
git status
git add train.py configs/retrain-v2.json data/manifests/dataset-marine-v2.csv
git commit -m "Prepare reviewed marine data retraining"
git tag dataset-marine-v2
```

모델 바이너리와 이미지 데이터가 크다면 별도 저장소에 두고, Git에는 버전과 저장 위치를 기록합니다. 모델 파일을 Git 커밋에 넣을지 여부는 파일 크기와 저장 정책에 따라 결정합니다.

Docker를 사용하면 학습에 필요한 Python 실행 환경을 이미지로 고정할 수 있습니다. 재학습에 사용하는 라이브러리 버전을 기록하고, 검증된 이미지 태그를 붙입니다.

```bash
docker build -t fish-training:dataset-marine-v2 .
docker run --rm `
  -v "${PWD}/data:/app/data" `
  -v "${PWD}/artifacts:/app/artifacts" `
  fish-training:dataset-marine-v2
```

Windows PowerShell에서는 줄 연결 기호가 위 예시와 같습니다. 셸에 따라 줄 연결 방식이 달라질 수 있습니다. 데이터와 모델 아티팩트는 컨테이너 이미지에 무조건 포함하기보다, 필요한 위치를 볼륨이나 별도 저장소로 연결할 수 있습니다.

## 11. 배포와 모니터링

후보 모델이 승인되면 운영 서버가 사용할 모델 버전을 바꿉니다. 배포 후에는 다음 지표를 관찰합니다.

- 추론 성공률과 오류율
- 평균 및 상위 구간 응답 시간
- 클래스별 예측 분포의 변화
- confidence 분포의 변화
- 사용자 검토에서 확인된 오분류율
- 모델 버전별 사용 건수

새 모델의 결과가 악화되거나 서버 오류가 증가하면 이전 운영 버전으로 되돌릴 수 있어야 합니다. 롤백할 모델 파일과 FastAPI가 기대하는 클래스 목록·전처리 설정을 함께 보존합니다.

## 12. 전체 재학습 절차 정리하기

```text
1. 서비스 예측과 오분류 신고 수집
2. 전문가가 정답과 이미지 품질 검토
3. 사용 가능한 자료를 dataset 버전으로 고정
4. 학습·검증·테스트 자료 분리
5. Docker 환경과 Git 커밋을 기록하고 재학습
6. 기존 모델과 후보 모델 평가
7. 승인된 후보만 운영에 배포
8. 결과를 모니터링하고 필요하면 롤백
```

각 단계의 입력과 결과를 기록하면 같은 결과를 재현하거나 실패 원인을 조사하기 쉽습니다.

## 실습: 검토 완료 오분류 자료로 후보 모델 만들기

- 검토가 끝난 자료만 재학습 후보로 선택합니다.
- Manifest에 학습 자료의 ID와 라벨을 기록합니다.
- 학습·검증·테스트 분할과 데이터 누수 방지 기준을 정합니다.
- 새 모델을 기존 운영 모델을 덮어쓰지 않는 경로에 저장합니다.
- 기존 모델과 후보 모델의 평가 결과를 비교합니다.
- Git 커밋·데이터셋 버전·Docker 이미지 태그를 기록합니다.

## 핵심 정리

- 운영에서 수집한 예측 결과는 검토된 정답 라벨과 연결해야 재학습에 사용할 수 있습니다.
- 오분류 자료는 품질 검사와 중복 확인을 거쳐 버전이 지정된 데이터셋에 추가합니다.
- 학습·검증·테스트 데이터가 겹치지 않도록 분할 기준을 기록합니다.
- 후보 모델은 기존 운영 모델과 같은 기준으로 평가한 뒤 승인합니다.
- 모델·데이터셋·코드 커밋·Docker 환경의 버전을 연결하면 재현성이 높아집니다.
- 배포 뒤 지표를 모니터링하고 문제가 생기면 이전 모델로 롤백할 수 있어야 합니다.
- 다음 수업에서는 Docker로 풀스택 AI 서비스의 컨테이너 구성을 준비합니다.
