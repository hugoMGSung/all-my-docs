
## 들어가며

앞 장에서는 데이터 피드백 루프와 모델 버전 관리의 기초를 살펴봤습니다. 이번 장에서는 웹 서비스 API에 로그인한 사용자의 요청인지 확인하는 **JWT 인증**을 적용하고, 스마트 양식장 서비스를 클라우드에 배포할 때 고려할 구성을 정리합니다.

JWT는 토큰을 사용하는 인증 방식 중 하나입니다. 서버는 토큰의 서명과 만료 시각을 확인해 요청 주체를 식별합니다. 오늘은 Node.js API에 인증 미들웨어를 추가하고, Docker·Git을 활용해 배포 준비 흐름을 구성합니다.

## 1. 인증과 인가

인증(Authentication)은 사용자가 누구인지 확인하는 과정입니다. 인가(Authorization)는 확인된 사용자가 특정 기능이나 데이터에 접근할 권한이 있는지 판단하는 과정입니다.

```text
로그인 정보 확인 → 인증 성공 → JWT 발급
요청에 JWT 첨부 → 토큰 검증 → 역할·권한 확인 → API 실행
```

예를 들어 양식장 관측 자료 조회는 일반 사용자에게 허용하고, 사용자 관리나 모델 교체는 관리자에게만 허용할 수 있습니다. 토큰이 유효하다는 것만으로 모든 작업을 허용해서는 안 됩니다.

## 2. JWT 구조 이해하기

JWT는 보통 점으로 구분된 세 부분으로 구성됩니다.

```text
header.payload.signature
```

- Header: 토큰 종류와 서명 알고리즘 정보
- Payload: 사용자 ID, 역할, 발급 시각, 만료 시각 등 클레임
- Signature: 토큰이 발급 후 변경되지 않았음을 확인하는 서명

JWT의 Payload는 기본적으로 암호화된 비밀 저장소가 아닙니다. Base64URL 인코딩으로 읽을 수 있으므로 비밀번호, API 키, 개인정보 같은 민감한 값을 넣으면 안 됩니다. 서명은 변조를 탐지하기 위한 것이며 내용 숨김과는 다릅니다.

## 3. 토큰 발급과 전달 방식

로그인 정보가 확인되면 서버가 서명된 토큰을 발급합니다. 브라우저는 이후 요청의 `Authorization` 헤더에 Bearer 토큰을 포함할 수 있습니다.

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

토큰에는 필요한 식별 정보와 권한만 최소한으로 넣고, 짧은 만료 시간을 설정합니다. 운영 환경에서는 HTTPS를 사용해 전송 중 토큰이 노출되지 않도록 합니다.

토큰을 브라우저에 저장하는 방식에는 XSS·CSRF 등 서로 다른 위험이 있으므로 서비스의 위협 모델에 맞게 결정해야 합니다. 민감한 서비스에서는 보안 속성을 설정한 HttpOnly 쿠키, CSRF 방어, 짧은 액세스 토큰과 갱신 전략 등을 함께 설계합니다. 브라우저 저장소에 장기 유효 토큰을 보관하는 방식은 신중히 검토합니다.

## 4. Node.js 프로젝트에 JWT 적용 준비하기

Node.js 프로젝트에 JWT 라이브러리를 설치합니다.

```bash
npm install jsonwebtoken
```

`.env` 파일에 서명 비밀키를 추가합니다.

```text
JWT_SECRET=여기에_충분히_긴_임의의_비밀값을_설정
JWT_EXPIRES_IN=15m
```

`JWT_SECRET`은 개발용 예시를 그대로 운영에 사용하지 않습니다. 충분히 예측하기 어려운 값으로 생성하고, Git에 커밋하거나 공개 채팅·로그에 기록하지 않습니다. `.gitignore`에서 `.env`가 제외되어 있는지 확인합니다.

## 5. JWT 발급 코드 작성하기

로그인 자격 증명이 검증된 뒤 토큰을 발급하는 함수를 작성합니다. 아래 함수는 비밀번호를 검증하지 않으며, 사용자 저장소에서 검증을 마친 사용자 정보를 전달받는다는 전제입니다.

```javascript
const jwt = require("jsonwebtoken");

function createAccessToken(user) {
  if (!process.env.JWT_SECRET) {
    throw new Error("JWT_SECRET 환경 변수가 설정되어 있지 않습니다.");
  }

  return jwt.sign(
    {
      role: user.role
    },
    process.env.JWT_SECRET,
    {
      subject: String(user.id),
      expiresIn: process.env.JWT_EXPIRES_IN || "15m",
      algorithm: "HS256",
      issuer: "smart-aquaculture-api",
      audience: "smart-aquaculture-web"
    }
  );
}
```

`subject`는 토큰의 주체인 사용자 ID를 나타냅니다. `expiresIn`은 유효 기간을 설정합니다. `issuer`와 `audience`를 지정하면 토큰이 어디서 발급되어 누구를 대상으로 하는지 검증할 수 있습니다.

실제 로그인 API에서는 사용자가 입력한 비밀번호를 저장된 해시와 안전하게 비교한 뒤에만 토큰을 발급합니다. 비밀번호를 평문으로 저장하거나 JWT Payload에 포함하지 않습니다.

## 6. 인증 미들웨어로 토큰 검증하기

보호할 API의 앞단에서 `Authorization` 헤더를 읽고 토큰을 검증합니다.

```javascript
function requireAuth(request, response, next) {
  const authorization = request.headers.authorization;

  if (!authorization?.startsWith("Bearer ")) {
    return response.status(401).json({
      message: "인증 토큰이 필요합니다."
    });
  }

  const token = authorization.slice("Bearer ".length);

  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET, {
      algorithms: ["HS256"],
      issuer: "smart-aquaculture-api",
      audience: "smart-aquaculture-web"
    });

    request.user = {
      id: payload.sub,
      role: payload.role
    };

    next();
  } catch (error) {
    return response.status(401).json({
      message: "토큰이 유효하지 않거나 만료되었습니다."
    });
  }
}
```

`jwt.verify()`는 서명, 알고리즘, 발급자, 대상, 만료 등의 조건을 확인합니다. 디코딩만 하는 `jwt.decode()`는 서명을 검증하지 않으므로 인증 판단에 사용하지 않습니다.

관측 데이터 조회 API에 인증 미들웨어를 적용합니다.

```javascript
app.get("/api/observations", requireAuth, async (request, response, next) => {
  try {
    const db = getDatabase();
    const items = await db.collection("observations").find({}).toArray();
    response.json({ items, count: items.length });
  } catch (error) {
    next(error);
  }
});
```

인증이 필요한데 토큰이 없거나 유효하지 않으면 `401 Unauthorized`를 반환합니다. 토큰이 유효해도 권한이 부족하면 `403 Forbidden`을 반환합니다.

## 7. 역할에 따라 권한 확인하기

인증 이후 사용자의 역할을 확인하는 인가 미들웨어를 만들 수 있습니다.

```javascript
function requireRole(...allowedRoles) {
  return (request, response, next) => {
    if (!request.user) {
      return response.status(401).json({ message: "로그인이 필요합니다." });
    }

    if (!allowedRoles.includes(request.user.role)) {
      return response.status(403).json({ message: "접근 권한이 없습니다." });
    }

    next();
  };
}
```

관리자 전용 경로에는 인증과 역할 확인을 차례로 적용합니다.

```javascript
app.post(
  "/api/admin/models/activate",
  requireAuth,
  requireRole("admin"),
  activateModelHandler
);
```

서버는 프론트엔드가 숨긴 버튼만 믿어서는 안 됩니다. 브라우저에서 버튼을 감추더라도 API 요청을 직접 보낼 수 있으므로, 권한 검사는 서버에서 수행합니다.

## 8. 클라우드 배포 구조 설계하기

서비스는 역할별로 분리해 배포할 수 있습니다.

```text
브라우저
   ↓ HTTPS
웹 프론트엔드 정적 호스팅
   ↓ HTTPS API 요청
Node.js 백엔드
   ├─ MongoDB 관리형 데이터베이스
   ├─ 이미지 오브젝트 스토리지
   └─ FastAPI 추론 서비스
         ↓
       CPU/GPU 실행 자원
```

배포 환경에서는 각 서비스가 맡는 책임과 네트워크 경계를 명확히 합니다. 예를 들어 MongoDB를 인터넷 전체에 공개하지 않고 백엔드만 접근하게 하고, FastAPI도 공개가 꼭 필요하지 않다면 내부 네트워크에서 Node.js만 호출하도록 구성합니다.

## 9. 배포 전 환경 설정 점검하기

로컬 개발 설정을 그대로 클라우드에 복사하지 않습니다. 배포 환경마다 필요한 설정을 분리합니다.

- `MONGODB_URI`: 관리형 MongoDB 연결 정보
- `AI_SERVER_URL`: FastAPI 내부 또는 서비스 주소
- `JWT_SECRET`: 배포 환경의 비밀 관리 기능에서 주입
- `PORT`: 플랫폼이 지정한 포트 또는 서비스 설정
- 이미지 저장소 주소와 자격 증명
- 허용할 프론트엔드 도메인(CORS 설정)

비밀값은 소스 코드나 Docker 이미지에 포함하지 않습니다. 클라우드 플랫폼의 Secret Manager나 환경 변수 설정 기능을 이용하고, 로그에도 토큰과 연결 문자열 전체를 남기지 않습니다.

## 10. Git과 Docker로 배포 준비하기

Git 커밋은 배포할 코드 버전을 확인하는 기준입니다.

```bash
git status
git add server.js package.json package-lock.json Dockerfile .dockerignore
git commit -m "Add JWT authentication middleware"
git tag release-1.0.0
```

배포할 코드를 커밋한 뒤 태그나 릴리스 기준점을 남기면 장애 발생 시 어떤 버전이 배포되었는지 확인하기 쉽습니다. `.env`, 토큰, 비밀번호, 데이터 파일은 커밋에 포함하지 않습니다.

Docker 이미지는 애플리케이션을 실행하는 환경을 묶습니다. 예를 들어 Node.js 백엔드의 최소 Dockerfile은 다음과 같이 구성할 수 있습니다.

```dockerfile
FROM node:22-slim

WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev

COPY . .

ENV NODE_ENV=production
EXPOSE 3000

CMD ["node", "server.js"]
```

`.dockerignore` 파일에는 불필요하거나 민감한 파일을 빌드 컨텍스트에서 제외하도록 작성합니다.

```text
node_modules
.env
.git
*.log
```

실제 배포에서는 신뢰할 수 있는 최소 베이스 이미지를 선택하고, 의존성과 베이스 이미지 업데이트를 관리합니다. 환경별 비밀값은 런타임에 주입합니다.

## 11. 배포와 롤백 전략

한 번에 모든 사용자에게 새 버전을 적용하기보다, 배포 환경의 기능을 이용해 단계적으로 전환할 수 있습니다.

- 새 버전을 별도 인스턴스에 배포해 기본 동작을 확인합니다.
- 일부 트래픽만 새 버전으로 보내 결과와 오류율을 살핍니다.
- 문제가 없으면 트래픽을 늘려 전체 전환합니다.
- 문제가 발견되면 이전 이미지 태그나 릴리스로 되돌립니다.

작은 수업 프로젝트에서는 플랫폼이 제공하는 이전 배포 복구 기능이나 이미지 태그를 사용해 롤백 흐름을 연습할 수 있습니다. 모델 API와 백엔드는 서로 다른 버전이 호환되는지 확인하고, 응답 JSON 계약을 갑자기 깨뜨리지 않도록 합니다.

## 12. 운영 상태와 헬스 체크

배포된 서버가 실행 중인지 확인할 수 있도록 상태 확인 API를 둡니다.

```javascript
app.get("/health", (request, response) => {
  response.json({ status: "ok" });
});
```

상태 확인은 프로세스가 살아 있는지 확인하는 기본 신호입니다. 필요하다면 데이터베이스 연결이나 추론 서버 연결을 확인하는 readiness 상태를 별도로 만들 수 있습니다. 외부 시스템 장애를 헬스 체크 하나로 처리하는 방식은 배포 플랫폼의 재시작 반복을 일으킬 수 있으므로, liveness와 readiness의 목적을 나누어 설계합니다.

배포 후에는 다음을 확인합니다.

- HTTPS로 접속되는가?
- 인증 없는 요청은 보호된 API에 접근하지 못하는가?
- 유효하지 않은 토큰과 권한 부족을 구분하는가?
- 데이터베이스와 추론 서버 연결이 정상인가?
- 로그에 토큰이나 비밀 연결 정보가 노출되지 않는가?
- 새 버전에 문제가 생겼을 때 이전 버전으로 되돌릴 수 있는가?

- 관측 데이터 API에 인증을 적용합니다.
- 관리자 전용 API에 역할 검사를 추가합니다.

## 오늘의 미션

- 인증과 인가의 차이를 설명합니다.
- JWT 세 부분의 역할과 Payload가 암호화되지 않는다는 점을 설명합니다.
- 토큰 만료·서명 검증·알고리즘 제한의 목적을 설명합니다.
- `401`과 `403` 응답의 차이를 설명합니다.
- 클라우드 환경에서 비밀값을 안전하게 주입하는 방법을 정합니다.

- 배포 후 확인 항목과 롤백 방법을 제안합니다.

## 핵심 정리

- 인증은 사용자를 확인하고, 인가는 사용자 권한을 확인합니다.
- JWT는 서명된 토큰이며 Payload에 민감한 비밀정보를 넣지 않습니다.
- 서버는 JWT 서명, 알고리즘, 만료 시간, 발급자와 대상을 검증해야 합니다.
- 프론트엔드의 화면 제어만으로 권한을 보호할 수 없으므로 서버에서 인가를 수행합니다.
- 클라우드 배포에서는 HTTPS, 비밀정보 관리, 네트워크 접근 제어, 상태 확인을 함께 고려합니다.
- Git 커밋과 Docker 이미지 태그를 연결하면 배포 버전과 롤백 대상을 추적하기 쉽습니다.
- 다음 수업에서는 서비스에서 수집된 오분류 데이터를 재학습에 활용하는 과정을 다룹니다.
