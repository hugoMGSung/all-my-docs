
## 들어가며

앞 장에서는 React 웹, Node.js API, FastAPI 추론 서버, MongoDB를 각각 Docker 컨테이너로 실행했습니다. 이번 장에서는 이 서비스들을 하나의 `compose.yaml`에 선언하고, **Docker Compose로 스마트 양식장 모니터링 웹을 완성해 배포 테스트**합니다.

Compose는 여러 컨테이너 서비스, 네트워크, 볼륨, 환경 설정을 한 파일에서 관리하도록 도와줍니다. 오늘은 컨테이너가 서로 올바른 주소로 연결되는지, MongoDB 데이터가 유지되는지, 브라우저에서 전체 서비스 흐름이 동작하는지 확인합니다.

## 1. 완성할 서비스 구성

```text
브라우저
   ↓ http://localhost:8080
web (React 정적 파일 + Nginx)
   ↓ /api 요청 전달
api-server (Node.js + Express)
   ├─ mongodb (MongoDB + 영속 볼륨)
   └─ ai-server (FastAPI + PyTorch 모델)
```

각 서비스의 책임은 다음과 같습니다.

| 서비스 | 역할 | 내부 포트 |
|---|---|---:|
| `web` | React 화면 제공, `/api` 요청을 백엔드에 전달 | 80 |
| `api-server` | 로그인·관측 데이터·추론 요청 API 처리 | 3000 |
| `ai-server` | PyTorch 모델로 이미지 추론 | 8000 |
| `mongodb` | 관측 자료와 추론 결과 저장 | 27017 |

브라우저는 `web`만 접근하고, Node.js와 FastAPI, MongoDB 통신은 Compose 내부 네트워크에서 처리합니다.

## 2. 프로젝트 폴더 확인하기

프로젝트가 다음과 같은 구조라고 가정합니다.

```text
smart-aquaculture/
├─ compose.yaml
├─ .env
├─ .env.example
├─ .gitignore
├─ web/
│  ├─ Dockerfile
│  ├─ nginx.conf
│  └─ ... React 프로젝트 파일
├─ api/
│  ├─ Dockerfile
│  ├─ server.js
│  └─ ... Node.js 프로젝트 파일
└─ ai_server/
   ├─ Dockerfile
   ├─ main.py
   ├─ requirements.txt
   └─ models/
      ├─ fish_classifier.ts
      └─ classes.json
```

각 폴더의 Dockerfile과 애플리케이션 코드는 13일차에 준비했습니다. 파일 위치가 다르면 Compose의 `build.context`와 Dockerfile 경로를 실제 프로젝트에 맞게 수정합니다.

## 3. 환경 변수와 비밀정보 준비하기

Compose 프로젝트 루트에 `.env.example` 파일을 만들어 필요한 값을 설명합니다.

```text
MONGO_USER=appuser
MONGO_ROOT_PASSWORD=replace-with-a-secure-password
MONGO_DATABASE=smart_aquaculture
JWT_SECRET=replace-with-a-long-random-secret
```

`.env.example`을 복사해 로컬 실행용 `.env`를 만듭니다. `.env`는 Git에 커밋하지 않습니다.

```text
.env
```

위 줄이 `.gitignore`에 있는지 확인합니다. `.env.example`에는 실제 비밀값을 넣지 않고, 변수 이름과 작성 예시만 둡니다. 실제 클라우드 환경에서는 플랫폼의 비밀 관리 기능으로 값을 전달합니다.

MongoDB 비밀번호에 `@`, `:`, `/`, `?`, `#` 같은 문자가 포함되면 연결 URI에서 URL 인코딩이 필요할 수 있습니다. 학습 환경에서는 URI에 안전하게 사용할 수 있는 임의의 값을 준비하거나, 사용자 이름과 비밀번호를 별도 환경 변수로 전달하는 방식을 고려합니다.

## 4. Compose 파일 작성하기

프로젝트 루트에 `compose.yaml` 파일을 만들고 다음과 같이 작성합니다.

```yaml
services:
  mongodb:
    image: mongo:7
    restart: unless-stopped
    environment:
      MONGO_INITDB_ROOT_USERNAME: ${MONGO_USER:?MONGO_USER를 설정하세요}
      MONGO_INITDB_ROOT_PASSWORD: ${MONGO_ROOT_PASSWORD:?MONGO_ROOT_PASSWORD를 설정하세요}
    volumes:
      - mongo-data:/data/db
    healthcheck:
      test:
        [
          "CMD-SHELL",
          "mongosh --quiet -u \"$$MONGO_INITDB_ROOT_USERNAME\" -p \"$$MONGO_INITDB_ROOT_PASSWORD\" --authenticationDatabase admin --eval \"db.adminCommand('ping').ok\""
        ]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 15s

  ai-server:
    build:
      context: ./ai_server
      dockerfile: Dockerfile
    restart: unless-stopped
    expose:
      - "8000"
    healthcheck:
      test:
        [
          "CMD",
          "python",
          "-c",
          "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=3)"
        ]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s

  api-server:
    build:
      context: ./api
      dockerfile: Dockerfile
    restart: unless-stopped
    environment:
      NODE_ENV: production
      PORT: 3000
      DB_NAME: ${MONGO_DATABASE:-smart_aquaculture}
      MONGODB_URI: mongodb://${MONGO_USER}:${MONGO_ROOT_PASSWORD}@mongodb:27017/?authSource=admin
      AI_SERVER_URL: http://ai-server:8000
      JWT_SECRET: ${JWT_SECRET:?JWT_SECRET을 설정하세요}
    depends_on:
      mongodb:
        condition: service_healthy
      ai-server:
        condition: service_healthy
    expose:
      - "3000"
    healthcheck:
      test:
        [
          "CMD",
          "node",
          "-e",
          "fetch('http://127.0.0.1:3000/health').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"
        ]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 15s

  web:
    build:
      context: ./web
      dockerfile: Dockerfile
    restart: unless-stopped
    depends_on:
      api-server:
        condition: service_healthy
    ports:
      - "8080:80"

volumes:
  mongo-data:
```

Compose 파일의 `services` 아래에 실행할 서비스들을 정의합니다. `build.context`는 이미지 빌드에 사용할 폴더이고, `image`는 이미지를 가져올 때 사용합니다. `ports`는 호스트에 공개할 포트, `expose`는 Compose 네트워크 내부 서비스에 사용할 포트를 나타냅니다.

`depends_on`은 서비스 시작 순서를 정합니다. `condition: service_healthy`를 사용하면 의존 서비스가 실행 중인 것뿐 아니라 healthcheck에 통과할 때까지 기다릴 수 있습니다. 데이터베이스 컨테이너가 실행됐다고 해서 바로 쿼리를 받을 준비가 된 것은 아닐 수 있습니다.

`mongo-data`는 MongoDB의 데이터 디렉터리에 연결된 이름 있는 볼륨입니다. 컨테이너를 다시 만들어도 데이터가 유지되도록 합니다.

## 5. 내부 서비스 주소 확인하기

Compose는 기본 네트워크를 만들고 서비스 이름으로 이름 해석을 제공합니다. Node.js API는 다음 주소로 내부 서비스를 호출합니다.

```text
mongodb:27017
http://ai-server:8000
```

컨테이너 안에서 `localhost`는 해당 컨테이너 자신입니다. 따라서 API 컨테이너에서 `localhost:27017`을 사용하면 MongoDB 컨테이너가 아니라 API 컨테이너 자신을 가리킵니다.

브라우저는 Compose 네트워크 내부 이름을 사용할 수 없습니다. 브라우저는 호스트에 공개된 `http://localhost:8080`으로 웹을 요청하고, Nginx가 내부의 `api-server:3000`으로 `/api` 요청을 전달합니다.

## 6. 실행 전 설정 점검하기

Compose 파일을 실행하기 전에 다음을 확인합니다.

- Docker Desktop 또는 Docker Engine이 실행 중인가?
- Compose 플러그인을 사용할 수 있는가?
- 각 서비스 폴더에 Dockerfile이 있는가?
- 프론트엔드 Nginx 설정의 API 대상이 `api-server:3000`인가?
- Express 서버가 `0.0.0.0:3000`에서 요청을 받는가?
- FastAPI 서버가 `0.0.0.0:8000`에서 요청을 받는가?
- 각 서비스의 환경변수가 올바른가?
- `.env`가 Git과 Docker 빌드 컨텍스트에서 제외되어 있는가?
- AI 모델 파일과 클래스 목록이 AI 이미지에 포함되어 있는가?

Compose 설정이 올바른지 확인합니다.

```bash
docker compose config -q
```

필요하면 합쳐진 설정을 출력해 변수 치환 결과와 서비스 구성을 확인할 수 있습니다.

```bash
docker compose config
```

출력에 비밀값이 포함될 수 있으므로 로그나 공개 자료에 그대로 공유하지 않습니다.

## 7. 전체 서비스 빌드 및 실행하기

프로젝트 루트에서 다음 명령으로 모든 이미지를 빌드하고 서비스를 실행합니다.

```bash
docker compose up --build -d
```

- `up`은 서비스를 생성하고 실행합니다.
- `--build`는 필요한 이미지를 다시 빌드합니다.
- `-d`는 터미널을 점유하지 않고 백그라운드에서 실행합니다.

컨테이너 상태를 확인합니다.

```bash
docker compose ps
```

정상 실행이 되면 `mongodb`, `ai-server`, `api-server`, `web` 상태가 표시됩니다. `healthy` 상태가 필요한 서비스는 healthcheck 결과가 통과할 때까지 기다립니다.

## 8. 배포 테스트하기

컨테이너가 실행되는지만 확인하지 말고 브라우저 요청이 실제 API와 데이터베이스, 추론 서버까지 도달하는지 확인합니다.

### 1단계: 웹 화면 확인

브라우저에서 다음 주소를 엽니다.

```text
http://localhost:8080
```

React 대시보드가 열리고 정적 파일을 정상적으로 불러오는지 확인합니다.

### 2단계: Node.js health API 확인

브라우저나 HTTP 클라이언트에서 다음 API를 요청합니다. Nginx 설정에 `/api` 프록시 경로가 없다면 health 경로를 설정에 맞게 조정합니다.

```text
http://localhost:8080/api/health
```

Node.js가 반환한 상태 응답을 확인합니다.

### 3단계: MongoDB 데이터 흐름 확인

관측 데이터 목록 API를 호출합니다.

```text
http://localhost:8080/api/observations
```

로그인 인증을 적용했다면 유효한 토큰을 포함해 요청합니다. 빈 목록이어도 API가 정상 응답하면 백엔드와 MongoDB 연결을 확인할 수 있습니다.

### 4단계: AI 추론 서버 연결 확인

인증된 추론 요청을 보내 Node.js가 FastAPI를 호출하는지 확인합니다. 응답에서 예측 결과, 모델 버전, 처리 시간 등을 살펴봅니다.

### 5단계: 데이터 유지 확인

관측 자료를 등록한 뒤 서비스를 중지하고 다시 실행합니다.

```bash
docker compose stop
docker compose up -d
```

다시 관측 데이터 목록을 요청해 등록한 문서가 유지되는지 확인합니다. `mongo-data` 볼륨이 MongoDB 컨테이너의 데이터 경로에 연결되어야 합니다.

## 9. 서비스 로그와 오류 진단하기

전체 로그를 확인합니다.

```bash
docker compose logs
```

특정 서비스의 로그를 이어서 확인합니다.

```bash
docker compose logs -f api-server
docker compose logs -f ai-server
```

오류가 발생하면 서비스별로 점검합니다.

| 증상 | 확인할 내용 |
|---|---|
| `web`에서 API 502 응답 | Nginx `proxy_pass` 주소와 API 컨테이너 상태 |
| API가 MongoDB에 연결하지 못함 | URI 호스트가 `mongodb`인지, 계정·비밀번호·DB 이름이 맞는지 |
| API가 AI 서버에 연결하지 못함 | `AI_SERVER_URL`이 `http://ai-server:8000`인지 |
| healthcheck 실패 | 서비스가 올바른 포트와 경로에서 응답하는지 |
| AI 서버가 시작되지 않음 | 모델 파일 경로, Python 패키지, CPU/GPU 설정 |
| MongoDB 문서가 유지되지 않음 | `mongo-data` 볼륨이 `/data/db`에 연결됐는지 |
| 환경 변수 누락 | `.env` 존재 여부와 변수 이름 확인 |

## 10. Compose 서비스 운영 명령

실행 중인 로그를 확인하고, 특정 서비스만 다시 빌드하거나 재시작할 수 있습니다.

```bash
docker compose restart api-server
docker compose build api-server
docker compose up -d api-server
```

프로젝트를 중지하고 컨테이너와 Compose 네트워크를 정리합니다.

```bash
docker compose down
```

이 명령은 이름 있는 `mongo-data` 볼륨을 기본적으로 제거하지 않습니다. `docker compose down -v`는 볼륨까지 삭제해 데이터가 사라질 수 있으므로, 유지해야 할 데이터가 있는 환경에서는 사용 전에 확인해야 합니다.

## 11. Git으로 배포 상태 기록하기

배포에 사용한 소스 코드와 Compose 설정을 Git으로 기록합니다.

```bash
git status
git add compose.yaml web api ai_server .env.example .gitignore
git commit -m "Deploy smart aquaculture stack with Compose"
git tag project-release-1.0.0
```

`.env`와 비밀값은 추가하지 않습니다. 배포 이미지 태그, Git 커밋, 모델 버전을 연결해 두면 어떤 소스와 모델 조합이 실행됐는지 추적하기 쉽습니다.

## 12. 배포 테스트 체크리스트

- Compose 설정이 오류 없이 해석되는가?
- 네 서비스가 모두 실행되고 필요한 healthcheck가 통과하는가?
- 웹 화면이 호스트 포트에서 열리는가?
- Nginx를 거쳐 Node.js API에 요청할 수 있는가?
- API가 MongoDB에서 자료를 읽고 저장하는가?
- API가 FastAPI 추론 결과를 받아 화면에 전달하는가?
- MongoDB 데이터를 컨테이너 재시작 뒤에도 읽을 수 있는가?
- 로그에 연결 문자열, JWT 토큰, 비밀번호가 남지 않는가?
- Git에 `.env`가 포함되지 않았는가?

## 실습: Docker Compose로 미니 프로젝트 배포하기

13일차의 개별 컨테이너 구성을 Compose로 옮기고 다음 결과를 완성합니다.

- `compose.yaml`에 web, api-server, ai-server, mongodb 서비스를 정의합니다.
- MongoDB 데이터를 named volume에 보존합니다.
- healthcheck와 `depends_on`으로 준비 순서를 지정합니다.
- Nginx에서 `/api`를 Node.js 서비스로 전달합니다.
- 환경 변수로 내부 서비스 주소와 데이터베이스 연결을 설정합니다.
- `docker compose up --build -d`로 전체 시스템을 실행합니다.
- 대시보드·관측 API·AI 추론·데이터 지속성을 확인합니다.
- 배포 소스와 설정을 Git 커밋 및 태그로 기록합니다.

## 오늘의 미션

- Compose가 관리하는 서비스, 네트워크, 볼륨의 역할을 설명합니다.
- 컨테이너 실행 상태와 healthcheck 상태의 차이를 설명합니다.
- `depends_on`의 `service_healthy`가 필요한 이유를 설명합니다.
- 컨테이너 내부 주소와 브라우저에서 접근하는 주소를 구분합니다.
- 관측 데이터가 컨테이너 재시작 후 유지되는지 확인합니다.
- 오류 로그를 바탕으로 웹·API·AI·DB 연결 문제를 진단합니다.
- 배포에 사용한 Git 커밋과 모델 버전을 기록합니다.

## 핵심 정리

- Docker Compose는 여러 컨테이너 서비스를 하나의 YAML 파일에서 관리합니다.
- Compose 네트워크에서는 서비스 이름을 호스트 주소로 사용합니다.
- `depends_on`과 healthcheck로 서비스 준비 상태에 따른 시작 순서를 제어할 수 있습니다.
- 이름 있는 볼륨은 MongoDB 같은 서비스의 데이터를 컨테이너 교체 후에도 유지합니다.
- 프론트엔드에서 API를 호출할 때 Nginx 프록시를 사용할 수 있습니다.
- 서비스 상태뿐 아니라 웹→API→AI·DB까지 실제 요청 흐름을 확인해야 합니다.
- `.env`와 비밀값은 Git에 커밋하지 않고 배포 환경에서 안전하게 주입합니다.
- 다음 수업에서는 프로젝트의 최종 성과를 정리하고 발표 자료와 리포트를 작성합니다.
