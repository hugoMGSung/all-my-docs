
## 들어가며

앞 장에서는 스마트 양식장 실시간 개체 모니터링 웹을 Docker Compose로 실행하고, 웹 화면부터 API·AI 추론·MongoDB까지 요청 흐름을 확인했습니다. 마지막 수업에서는 프로젝트의 결과와 과정을 정리해 **최종 성과 리포트**를 작성합니다.

좋은 성과 리포트는 기능 목록만 나열하지 않습니다. 어떤 문제를 해결하려 했는지, 어떤 구조로 구현했는지, 실제로 어떻게 확인했는지, 현재 한계는 무엇인지 근거와 함께 설명합니다. 측정하지 않은 성능 수치나 확인하지 않은 결과를 임의로 작성하지 않습니다.

## 1. 최종 성과 리포트의 목적

최종 리포트는 프로젝트를 수행한 과정과 결과를 다른 사람이 이해하고 재현할 수 있도록 정리한 문서입니다.

리포트는 다음 질문에 답해야 합니다.

- 어떤 문제나 요구사항을 해결했나요?
- 서비스의 구성 요소와 데이터 흐름은 어떻게 되나요?
- 어떤 기능을 구현했고 어떤 기술을 사용했나요?
- 기능이 정상 동작하는지 어떻게 확인했나요?
- 모델과 서비스의 결과를 어떤 근거로 평가했나요?
- 현재 구현하지 못한 점과 다음 개선 과제는 무엇인가요?

## 2. 보고서 전체 구성

아래 목차를 사용해 프로젝트 결과를 정리합니다.

```text
1. 프로젝트 개요
2. 문제 정의와 목표
3. 요구사항 및 구현 범위
4. 시스템 아키텍처와 데이터 흐름
5. 주요 구현 내용
6. 배포 환경과 실행 방법
7. 검증 결과와 평가
8. 문제 해결 과정
9. 역할 분담 및 기여 내용
10. 한계와 개선 계획
11. 결론
12. 참고자료 및 부록
```

목차는 프로젝트의 실제 범위에 맞게 조정할 수 있습니다. 팀 프로젝트라면 구성원별 역할과 기여 내용을 명확하게 작성합니다.

## 3. 프로젝트 개요와 문제 정의

첫 부분에서는 프로젝트의 목적과 해결하려는 문제를 짧게 설명합니다.

### 프로젝트 개요 예시 틀

```text
프로젝트명: 스마트 양식장 실시간 개체 모니터링 웹
프로젝트 기간: [실제 시작일] ~ [실제 종료일]
팀명 및 구성원: [팀명, 구성원]
담당 역할: [실제 담당 업무]
```

### 문제 정의 작성 예시 틀

```text
현재 [사용자 또는 현장]에서는 [어떤 어려움]이 발생한다.
이 프로젝트는 [어떤 데이터와 기능]을 활용해 [어떤 개선]을 제공하는 것을 목표로 한다.
```

문제 정의는 프로젝트에서 실제로 다룬 대상과 범위에 한정합니다. 현장 조사를 하지 않았다면 현장에서 확인된 사실처럼 단정하지 않고, 프로젝트의 가정이나 제안으로 표현합니다.

## 4. 요구사항과 구현 범위 정리하기

요구사항을 기능과 비기능 항목으로 구분합니다.

| 구분 | 요구사항 예시 | 구현 여부 | 근거 |
|---|---|---|---|
| 기능 | 관측 자료 조회 | 완료/부분/미구현 | API 응답 화면 또는 기록 |
| 기능 | AI 어종 분류 결과 표시 | 완료/부분/미구현 | 추론 결과 화면 |
| 기능 | 이미지 위 탐지 영역 표시 | 완료/부분/미구현 | Bounding Box 화면 |
| 기능 | 수온 시계열 그래프 | 완료/부분/미구현 | 차트 화면 |
| 기능 | 서비스 컨테이너 배포 | 완료/부분/미구현 | Compose 실행 화면 |
| 비기능 | API 인증 적용 | 완료/부분/미구현 | 인증 요청 결과 |
| 비기능 | 데이터 지속성 | 완료/부분/미구현 | 재시작 전후 조회 결과 |

`완료`, `부분`, `미구현` 중 실제 상태를 기록합니다. 근거 열에는 확인 방법이나 캡처·로그·파일명을 씁니다. 아직 구현하지 않은 기능을 완료로 표현하지 않습니다.

## 5. 시스템 구조와 데이터 흐름 설명하기

시스템 구성도를 포함하고 각 서비스가 어떤 일을 하는지 설명합니다.

```text
브라우저
   ↓ HTTPS 또는 개발용 HTTP
React + Nginx
   ↓ /api 요청
Node.js + Express
   ├─ MongoDB: 관측·검토 자료
   └─ FastAPI: 추론 요청
        ↓
      PyTorch 어종 분류 모델
```

그림 아래에는 데이터 흐름을 단계별로 씁니다.

1. 사용자가 웹 화면에서 양식장이나 관측 자료를 선택합니다.
2. React 화면이 Node.js API에 요청을 보냅니다.
3. Node.js가 인증·요청 검증 후 MongoDB에서 자료를 조회합니다.
4. 이미지 분석 요청은 FastAPI와 PyTorch 모델로 전달됩니다.
5. 추론 결과가 JSON으로 Node.js와 화면에 전달됩니다.
6. 화면은 관측 요약·차트·이미지 탐지 결과를 표시합니다.

실제 프로젝트에 적용하지 않은 기능이나 연결은 그림에서 제거하거나 향후 계획으로 표시합니다.

## 6. 주요 구현 내용 작성하기

기능별로 목표, 구현 방법, 확인 근거를 정리합니다.

| 기능 | 구현 방법 | 확인 근거 |
|---|---|---|
| 관측 자료 관리 | Express API와 MongoDB 문서 | 요청·응답, DB 조회 |
| 데이터 적재 | 공공데이터 정제 및 중복 방지 적재 | 입력·통과·제외 건수 |
| 어종 분류 | FastAPI와 PyTorch 모델 | 모델 버전 및 추론 응답 |
| 탐지 결과 화면 | React 컴포넌트와 Canvas | 이미지와 상자 표시 |
| 시계열 차트 | React와 Chart.js | 시간별 관측 그래프 |
| 컨테이너 배포 | Docker Compose | 서비스 상태와 로그 |

스크린샷은 화면만 보여주는 데 그치지 말고, 어떤 요구사항을 확인하는 자료인지 캡션을 붙입니다. 코드 전체를 보고서에 복사하기보다 핵심 구조와 중요한 처리만 설명하고 저장소나 부록을 참조합니다.

## 7. 실행 및 배포 방법 문서화하기

다른 사람이 프로젝트를 실행할 수 있도록 사전 조건과 순서를 기록합니다.

```text
필요한 도구: Docker Desktop 또는 Docker Engine, Docker Compose
설정 파일: .env.example을 복사해 로컬 .env 작성
실행 명령: docker compose up --build -d
접속 주소: http://localhost:8080
상태 확인: docker compose ps
로그 확인: docker compose logs -f [서비스명]
종료 명령: docker compose down
```

실제 포트, 경로, 환경 변수명은 프로젝트와 일치시킵니다. 비밀번호, JWT 비밀키, DB 연결 문자열과 같은 실제 비밀값은 보고서에 적지 않습니다. 공유가 필요한 환경 변수는 이름과 용도만 설명합니다.

## 8. 검증 결과와 평가 작성하기

각 기능을 어떤 입력으로 확인했고 실제로 어떤 결과가 나왔는지 씁니다.

| 검증 항목 | 입력 또는 조건 | 기대 결과 | 실제 결과 | 상태 |
|---|---|---|---|---|
| 관측 목록 조회 | 등록된 관측 자료 요청 | 자료 배열과 개수 반환 | [실제 확인 결과] | 통과/실패 |
| 인증 검사 | 토큰 없이 보호 API 요청 | `401` 응답 | [실제 확인 결과] | 통과/실패 |
| 추론 요청 | 테스트 이미지와 관측 ID | JSON 예측 결과 반환 | [실제 확인 결과] | 통과/실패 |
| 차트 표시 | 시간별 수온 자료 | 시간 순 선 그래프 | [실제 확인 결과] | 통과/실패 |
| Compose 상태 | 전체 서비스 시작 | 서비스 실행 및 준비 상태 | [실제 확인 결과] | 통과/실패 |
| 데이터 유지 | DB 자료 등록 후 재시작 | 기존 문서 조회 가능 | [실제 확인 결과] | 통과/실패 |

AI 모델 평가 수치를 보고할 때는 평가 데이터와 측정 방법을 함께 기록합니다.

```text
평가 데이터: [데이터셋 버전과 샘플 수]
평가 방법: [분리 기준, 측정 절차]
정확도: [실제로 측정한 값]
Macro F1: [실제로 측정한 값]
추론 시간: [장비 및 측정 방법과 함께 기록]
```

수치를 측정하지 않았다면 `미측정` 또는 `평가하지 않음`으로 적고, 추후 평가 계획을 제시합니다. 작은 샘플로 얻은 결과를 일반적인 성능처럼 확대해석하지 않습니다.

## 9. 문제 해결 과정 기록하기

문제 해결 과정은 오류 메시지만 나열하지 않고 원인 확인과 조치 결과를 정리합니다.

| 증상 | 원인 분석 | 조치 | 결과 |
|---|---|---|---|
| API에서 DB 연결 실패 | 컨테이너 내부 연결 주소 확인 | `localhost`를 Compose 서비스 이름으로 변경 | [실제 결과] |
| 모델 서버 시작 실패 | 모델 파일 경로와 환경 확인 | 경로·이미지 복사 설정 수정 | [실제 결과] |
| Bounding Box 위치 어긋남 | 이미지와 Canvas 크기 기준 불일치 | 이미지 표시 크기와 좌표 변환 보정 | [실제 결과] |

프로젝트에서 실제로 겪은 문제만 기록합니다. 해결하지 못한 문제는 숨기지 않고 현재 상태와 영향, 다음 조치 계획을 설명합니다.

## 10. 팀 역할과 기여도 작성하기

팀 프로젝트라면 각 구성원의 업무를 구체적으로 씁니다.

| 구성원 | 담당 업무 | 산출물 또는 기여 근거 |
|---|---|---|
| [이름] | [예: 데이터 정제·DB 적재] | [스크립트, 문서, 검토 기록] |
| [이름] | [예: FastAPI 추론 서버] | [API 코드, 모델 연동] |
| [이름] | [예: React 대시보드] | [컴포넌트, 차트, 화면] |
| [이름] | [예: Docker Compose 통합] | [compose 파일, 배포 기록] |

업무가 겹친 경우 공동 작업 범위를 설명합니다. 기여도를 수치로 요구받지 않았다면 근거 없는 퍼센트를 임의로 부여하지 않습니다.

## 11. 한계와 개선 계획

한계는 프로젝트를 낮게 평가하기 위한 항목이 아니라, 현재 결과의 적용 범위를 정확히 설명하는 부분입니다.

예를 들어 다음 항목을 확인할 수 있습니다.

- 학습 이미지의 어종·조명·수질 조건이 제한적인가?
- 모델이 현장 데이터에서 검증되었는가?
- 실제 카메라 스트림 대신 파일 업로드나 샘플 이미지를 사용했는가?
- API에 동시 요청·장시간 추론을 위한 큐가 없는가?
- 인증·권한·로그·백업이 운영 수준으로 구성되었는가?
- 클라우드 GPU 비용과 확장성 검토가 남아 있는가?

개선 계획은 구체적으로 씁니다.

```text
현재 한계: [확인된 한계]
영향: [사용자나 성능에 미치는 영향]
개선 작업: [다음에 할 일]
완료 기준: [어떤 조건이면 개선됐다고 판단할지]
```

## 12. 최종 발표 흐름 구성하기

짧은 발표는 다음 순서로 구성할 수 있습니다.

1. 해결하려는 문제와 대상 사용자
2. 구현 목표와 범위
3. 시스템 아키텍처와 데이터 흐름
4. 핵심 기능 시연
5. 검증 결과와 측정 근거
6. 어려웠던 점과 해결 과정
7. 한계 및 다음 개선 계획

시연에서는 정상 동작뿐 아니라 실제 입력, API 응답, 배포 상태 등 결과를 뒷받침하는 근거를 함께 보여줍니다. 네트워크나 모델 서버 문제가 생길 경우를 대비해 캡처나 짧은 녹화 등 대체 자료를 준비하되, 실제 시연이 아니라고 명확히 표시합니다.

## 핵심 정리

- 최종 성과 리포트는 목표·구현·검증·한계·개선 계획을 근거와 함께 설명합니다.
- 구현 여부와 성능 수치는 실제 확인 결과를 기준으로 작성합니다.
- 서비스 구성도와 데이터 흐름은 완성된 프로젝트와 일치해야 합니다.
- 실행 방법에는 필요한 환경, 설정, 명령, 접속 주소를 포함합니다.
- 모델 평가에는 데이터와 측정 방법을 함께 기록합니다.
- 해결하지 못한 문제도 영향과 후속 조치를 정리하면 결과의 적용 범위를 명확히 할 수 있습니다.
- 15일간의 프로젝트 결과를 리포트와 발표로 정리해 전체 과정을 마무리합니다.
